# 性能上限、数据流与融合取舍

用于解释热点为何慢、选择结构改动，或判断是否值得继续。HIP 与 Triton 共用；简单热点先做 FLOPs/字节与实测的粗估，只有解释不通或决定依赖某项资源时再展开。已有同条件的可信分析可复用，不要求每轮重建模型、填齐所有指标或先完成完整报告才能实验。

## 1. 从实测问题选择分析深度

先确认目标 kernel、shape/dtype/layout、实际分派与计时范围，把单 kernel、完整算子（必要时前向加反向）、模型端到端分开。用真实热点占比和可改善时间排序；同一形态已领先另一实现，也不等于没有优化价值。

- 简单流式或矩阵热点：先估必要字节、对应计算路径的工作量与可达吞吐，和未开启 profiler 的时间比较。
- 算力、HBM 利用率都不高：查小网格、串行递推、launch、地址/特殊函数、发射与等待，不直接归为某一种延迟瓶颈。
- 单 kernel 看似已忙、完整算子仍慢：看中间张量交接、重复计算、布局转换及前后向状态策略。
- trace 显示几乎无空隙但短 kernel 总耗时异常：核对 profiler 时间戳语义和采集扰动。有些版本会把排队/派发成本并入设备区间；连续时间线不证明没有派发开销，也不能再把 launch 成本无条件加一遍。

遇到优化瓶颈仍按 [性能分析入口](dcu_metrics_guide.md) 采集；本页帮助解释证据，不用估算替代所需 profiling。

## 2. 区分工作量与时间参照

多 kernel 或融合问题可按下面四个视角逐步展开，只写影响决策的部分：

| 视角 | 要算什么 | 帮助回答 |
| --- | --- | --- |
| 算法必要工作 | 在既定语义、精度、状态保存/重算策略下的必要运算和外部数据；不可避免的依赖链 | 理想化重组可能打开多大空间？ |
| 当前拆分接口 | 每个 kernel 实际使用的输入/输出、临时张量、布局副本和前后向交接 | 哪些交接或重复工作值得重组？ |
| 当前实现工作 | 执行的计算、padding/重算、各层 traffic、指令/请求与关键依赖 | 当前结构在何种资源上付了额外代价？ |
| 实测时间 | 未采集时的稳定时间，与对应版本/输入的 profile 对照 | 是否还有未解释的等待、竞争或测量偏差？ |

“每个输入读一次、每个输出写一次”是放宽片上容量等约束后的乐观估算，未必可实现。存储容量不是实际访问量；storage 去重也不能代替读写账目：读后原地写仍有两个方向，view 可能只访问部分 storage，多个消费者可能共享缓存，地址复用还需区分张量的生命周期和写入版本。记录关键中间量的生产者→消费者、访问范围、布局、读写次数及是否要保留到反向，不能仅凭指针相同推断同一份数据。

区分有用工作与实际执行工作。padding、重算或重复读取可以把硬件忙碌率抬高，却不提高有效效率；反过来，低 MFU 也不能单独说明矩阵计算需要优化。计算强度 `I = FLOPs / bytes` 要说明用的是必要 FLOPs 还是执行 FLOPs、接口字节还是某一存储层的实测字节。只有与相同计算路径和存储层的屋脊点 `P / BW` 比较才有解释力；混合算子还要拆开关键阶段看。

### 轻量时间模型

对一个 kernel，相关资源的工作量除以匹配吞吐，可给出乐观时间参照：

```text
t_est ≈ max(F_mmac / P_mmac, F_valu / P_valu,
            B_hbm / BW_hbm, B_lds / BW_lds,
            W_issue / R_issue, L_dependency, …)
```

省略未知或无关项并说明缺口，不把未知记成零。`max` 假定各资源能够理想重叠；共享发射通路、阶段串行、读写带宽耦合会改变结果。只对确实串行的阶段累加；多 stream/通信重叠按依赖图和资源竞争解释，不能拿所有 kernel 时间之和当端到端 wall time。launch 也按真实提交/执行路径处理。

- 区分**理论物理上限**与**同环境实测可达参照**。后者更实用，但测得的最快微基准不是不可突破的物理极限。计算路径、dtype/指令形式、读写比例、工作集/cache、频率和 grid 覆盖应与目标相符；借用标称值或其他环境的数值时标注不确定性。
- 先用已有硬件资料与同环境单测；只有分母不清且影响决策时才补相关微基准，不为每个算子全量标定硬件。微基准本身也要确认实际生成了预期代码。
- 算法、接口、实现的时间参照只有在相同边界和嵌套假设下才可能形成层级。缓存、不同计时范围或模型误差造成次序颠倒时，复核假设，不能排序/截断数值来凑分解。
- `t_est / t_measured` 是该模型下的效率参照；剩余差值不是承诺可回收时间。模型被实测超越时更新模型，不否定正确且可重复的实验。

## 3. 双轴 Roofline 解释不通时看什么

| 线索 | 核对与可选实验 |
| --- | --- |
| MMAC 很闲但计算不少 | 分开矩阵、VALU、特殊函数、整数地址/发射工作；用对应指令吞吐，不能全除以矩阵峰值。静态 ISA 数量不代表动态执行次数。 |
| VMEM/TA 很忙、HBM 不满 | 查每条访问的 lane 地址、跨度、缓存行/请求、合并与命中。TA busy 可能包含等数据返回，不能单独当作纯发射饱和；少了 VMEM 指令或改宽访问也不保证减少事务和时间。 |
| LDS conflict 或 wave wait 很高 | 先确认是否落在关键路径、其他 wave 是否能掩盖，再用有区分力的探针或前后 profile 判断。某个 wave 的等待百分比不能直接换成整个 kernel 的可回收百分比。 |
| Occupancy 低或 scratch 增长 | 分清理论驻留、实测驻留、grid 覆盖与尾部。按活跃 CU 归一化可解释局部效率，但同时保留整卡口径；不能用它掩盖未用到的 CU。查运行时索引、寄存器生存期与 spill，不机械追求最高 occupancy 或一律 scratch 为零。 |
| 相同单位工作的耗时随规模上升 | 按 token/head/tile 等归一化，核对并发 CTA 的地址间距、L2/TLB 局部性与访存通道竞争；grid 顺序本身也是候选维度，逐形态验证。 |
| 预取/双缓冲、减少指令反而变慢 | 查本次加载产物里的真实等待、alias 导致的保守排序、phi/register copy、生存期和请求发射节奏；源码中的异步不代表实际重叠。 |

这些是调查线索，不是硬件定律。不同 gfx、编译器和访问方式可能有相反结果；gfx936 的寄存器、vmcnt/LDS-DMA 或带宽经验不能直接推广到少伯、月英。低层修改按 [指令指南](hcu-isa-guide.md) 核对目标语义，`restrict` 等承诺只能用于契约保证不别名的指针。

需要 SQTT 定位时，绑定实际代码对象、dispatch、wave 和热循环，再关联源行/IR；符号不匹配或动态指令对齐覆盖不足时保留归因缺口。没有源码行映射可用已确认的 ISA/IR 位置，不能凭等待出现次数猜代码位置。

## 4. 融合、重算与布局一起算成本

先查已有 HCU 实现，再选择值得验证的候选。可从一个中间张量或一对生产/消费方开始，无须先建完整图：

- **能省什么**：实际能省的写回、读取、转换、launch；多个消费者仍需保留的数据不能全部算作已消除。融合组之间若有必须执行的外部依赖，不能直接合成一个 kernel；缓存命中交接不能全按 HBM 定价。
- **增加什么**：消费者中的重算/特殊函数、布局交换、同步、地址计算、重复生产。把一个生产者分别融入多个消费者可能复制多份工作；用消费者受限的资源估价，不能仅看减少了多少字节。
- **是否放得下、跑得满**：评估同时存活的寄存器/LDS、双缓冲、workspace、grid 并行度和 occupancy 改变。容量不足可考虑重分块/分阶段等新路线，不因一个方案放不下就否定整个融合方向。预留 LDS 等探针也可能改变缓存/调度，只作局部证据。
- **保存还是重算**：训练前向多保存中间状态有时能减少反向重算；比较完整前后向时间、峰值显存与张量寿命，遵守原任务精度和内存预算。保留状态不等同于单 kernel 融合，但也是可选结构优化。
- **并发是否真实**：独立数据的双 stream 实验只能测试竞争倾向。实际流水要保留生产消费依赖、同步与 buffer 生命周期，观察关键 kernel 是否被拖慢以及完整算子是否受益。

粗估用于排序和排除前提明确不成立的方案；对不确定、耦合较强的路线，可以做低成本探针，也可以直接实现一个可验证候选。探索路径不受模型阈值否决；模型与实测冲突时更新解释。数值约束沿用任务契约，不沿用 KDA 案例特有的 bitwise、容差或显存上限。

## 5. 用实验分清“看到了”与“确实导致了”

优先选择能区分解释的改动。消除一类 conflict、改变请求布局/发射节奏、分开测计算与等待，都应核对是否意外改变了其他工作量、分派或编译结果；删除代码可能引发死代码消除，产生虚假的收益归因。

**诊断探针与可交付候选分开。** 为估计贡献而跳过计算、屏障或写回的探针不一定语义正确；只在受控、无越界/竞争风险的独立实验中使用，不进入 best、正确候选或标准 `ablations`。它最多提供当前配置下的线索，甚至不能保证是严格上界。标准消融仍须保持完整语义。探针应验证剩余关键工作确实执行；基线变更后旧消融收益不能直接相加。

对较小或反常收益，除了同卡交替 A/B，还可检查 allocator/对齐、缓存状态、时钟、热稳态及其他进程。内循环重复不能当作多个独立进程样本；必要时用多次独立运行验证是否是内存位置或采集扰动。先看目标 kernel 的变化，再检查未改 kernel、完整算子和回归矩阵，不只留下最有利窗口。沿用原 Skill 的确认协议，不额外固定“五轮”或统一收益阈值。

跨平台参考尽量分开“不同实现、同一硬件”和“同一实现、不同硬件”；没有可运行组合就说明缺口。匹配语义、shape、精度、状态保存策略及时间范围。带宽视角的 `T = B / BW_achieved` 可帮助区分流量与吞吐，但由实测反算的恒等式不是独立因果证明；不能把另一张卡测出的 HBM 字节默认移用，也不能把双方都远离乐观下限直接归因成硬件极限。

## 6. 何时重开、何时收尾

沿用原任务目标和预算。收益停滞时，区分未减少的交接、实现额外工作和未掩盖等待，检查是否一直在同一结构上微调。先处理对总目标影响大的机会，同时考虑可实现程度、风险与实验成本；被其他阶段掩盖的局部热点不按原始时长直接算端到端收益。

收尾说明当前最好实现、剩余机会与约束、实测否定了哪些具体方案，哪些仍未知。停滞只表示在已试范围内未找到收益；“在当前精度/内存/硬件约束下接近可达参照”和“证明硬件极限”不同。shape、硬件、工具链、依赖或允许的精度/内存预算变化时，可以重新评估。

以上内容写进现有 `analysis.md`/报告即可：目标范围 → 主要成本与粗估参照 → 关键证据 → 候选/实测 → 限制和下一步。无需另建一套强制打分、审批或逐轮完整模型表。

## 7. 按需复用 KRA 工具

参考 [LearnMF/kernel-roofline-analysis-tools](https://github.com/LearnMF/kernel-roofline-analysis-tools)，本次核对提交 `9baf2a229197eada2edd6aef506cfd44414ce782`。三个 Skills 不依赖安装它；只是查方法、公式或实现时，直接在线阅读 GitHub 的文档及相关源码即可，下方有固定版本入口，不必 clone 全仓。需要运行批量分析、调试或离线查证时再下载到任务工具目录，记录版本并按该版 README/pyproject 核对依赖；输出放任务目录，不写入 Skill 安装目录。后续使用新版时复核实际源码差异。

| 工具入口（在 KRA 源码根目录运行） | 适合复用的内容 | 使用前核对 |
| --- | --- | --- |
| `python -m kra timeline --help` | hipprof trace 窗口、区间并集、可见空泡与计时对照 | 当前 trace schema、device/marker 和未采集基准的范围；不直接接任意 XProf `.perf` |
| `python -m kra calibrate --help` | 相关资源的微基准、ISA 与原始测量留存 | 当前 gfx/DTK 支持；按需选 bench；显式设任务内 `--build-dir`/`--out`，不照用示例机器分母 |
| `python -m kra pmc --help`、`python -m kra analyze --help` | PMC、op spec、接口捕获与资源参照表 | 精确计数器公式/重放匹配、真实算子映射、对应 machine 数据；缺项不当零，分类与停止标签只作线索 |
| `python -m kra.model.fusion --help` | 生产消费关系与候选合并的流量估算 | view/原地写/生命周期、外部依赖及实际 traffic；接口字节不等于 HBM 字节，节省时间不是收益保证 |
| `python -m kra.sqtt.pcmap --help` | 动态指令与热循环/源位置关联 | 明确本机 `--xcompute` 路径和兼容格式、真实 ISA/dispatch、对齐质量；wave 选择与 stall 归因是启发式 |

当前版本的 `kra/model/bounds.py`、PMC 语义和 `examples/kda/ceiling/cards.py` 有 gfx936/KDA 假设；示例中的固定机器、频率、矩阵 dtype、模板符号及经验阈值需重新核对。`LauncherCapture` 按 storage 统计，部分访问可能高估、原地输出可能漏算写入；报告使用前补读写语义。不要把自动结论直接转换成已验证瓶颈、硬件到顶或本工程 best 晋级状态。

本工程 `scripts/roofline.py` 仍是从已复核 normalized 指标分配实验预算的辅助工具，不是 KRA，也不自动计算本页的多层时间参照。KRA 报告按实际来源链接到任务分析，不覆盖原始测量，不新增必须依赖的服务或模型。
