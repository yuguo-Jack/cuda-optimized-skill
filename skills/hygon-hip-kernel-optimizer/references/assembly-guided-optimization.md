# 从汇编流水分析到编译后优化

HIP、Triton/Inductor 和已有库 kernel 共用的可选路线。适合解释源码与实测不一致、检查编译器留下的低层机会，或优化只有代码对象的实现。依据 AsmEvo 提炼方法，并适配本工程的 oracle、性能确认和 HCU 目标规则；不是已集成的 AsmEvo 执行器，也不是每轮必做的二进制改写流程。

## 1. 先选择在哪一层解决问题

源码表达的流水不一定是硬件执行的流水。反汇编可用于解释 load/compute/wait 的安排、活跃寄存器、spill、转换与地址计算，并据此修改 HIP/Triton；不必实际修改二进制才有价值。也不能从指令更少、文件更小或二进制不同直接推导更快。

| 当前证据与目的 | 可选路线 | 验证重点 |
| --- | --- | --- |
| 源码可读，怀疑 lowering、调度或资源分配不合理 | 把 profile 热点映射到最终 ISA，调整数据流、源码表达、编译配置或 builtin | 新构建是否真正改变目标指令/资源，是否改善实测瓶颈 |
| 编译器难以表达所需序列，目标工具链支持 | 局部 inline asm，或独立汇编 kernel 与原工程集成 | 寄存器约束、clobber、同步/内存语义、ABI 和全 kernel 回归 |
| 已有可重建代码对象，需要精确控制局部调度；也可能没有可编辑源码 | 恢复完整汇编，修改并重新汇编/链接 | 恢复忠实性、descriptor/metadata 一致性、实际加载与差分测试 |
| 完整重建暂不可行，且有可靠目标编码/补丁工具 | 隔离副本上的受限二进制补丁实验 | 指令边界、分支/重定位、资源与大小约束、可复现替换与回退 |

这些不是固定升级阶梯。证据充分时可直接选择汇编路线，无须先穷尽源码调参；如果源码改法更清晰、可维护，也不必为绕过编译器而改二进制。能否绕过的是某个 lowering/调度环节，不是目标 ISA、数值或同步约束。优先复用实际 HCU 分支的工具与汇编例子；AMD CDNA 的代码对象处理实现不能自动视为支持 HCU gfx。

## 2. 用动态证据选汇编热点窗口

1. 固定真实调用的 shape/dtype/stride、kernel 符号、gfx、工具链和加载产物；HIP 多文件/设备链接和 Triton JIT 特化均按 [指令指南](hcu-isa-guide.md) 核对对应关系。反汇编不支持时，先用该指南的实际工程汇编导出办法。
2. 遇到瓶颈按 [性能分析入口](dcu_metrics_guide.md) 采集。将当前工具支持的计数器、PC/指令采样或 SQTT 与实际 ISA 对齐，找重复执行且影响耗时的循环/区段。静态指令数不是动态工作量；单个 wave、一次采样或 wait 位置不能独自证明全 kernel 的原因。
3. 围绕热点读足够的上下文：load→首个消费者、独立计算、wait/barrier、寄存器 live-in/live-out、EXEC/分支、LDS/跨 wave 依赖与相关资源描述。等待常暴露上游供数或并发问题，不必是 wait 指令本身有问题。
4. 在现有分析里画出或简述“原安排→预期安排”，提出可证伪改动；必要时用小探针区分依赖、供数、资源或发射限制。工具缺失时标注静态假设，不能把静态图写成测得的指令 timeline。
5. 只把有关窗口及其依赖交给本轮实现上下文；修改后放回完整 kernel 验证。窗口大小由依赖决定，可扩大或改换热点，不要求固定行数、只允许局部改动或逐窗口机械遍历。

可考虑的方向及反例：

| 方向 | 可能改善什么 | 同时检查什么 |
| --- | --- | --- |
| load 提前、独立计算穿插、调整预取距离 | 隐藏长延迟，缩短消费者等待 | 生命周期变长、寄存器/occupancy、spill、越界与不同尾块；提前不等于更好 |
| wait 的位置或计数、同步范围 | 避免等待不相关工作，保持生产消费并行 | 精确 gfx 的计数器/完成语义、全部路径、跨 wave 可见性；不凭一次正确测试删 wait/barrier |
| cache hint、buffer/global/flat 或向量形式 | 访存请求、缓存与发射成本 | 地址空间、对齐/边界、返回值/原子/可见性、实际缓存与 traffic；不按指令名字判断快慢 |
| 缩短 live range、调整寄存器复用与布局 | 减少 spill 或资源限制，改变流水并发 | 新的数据依赖、重算/搬运、矩阵寄存器布局和实际分配粒度 |
| 减少转换、地址生成、冗余控制流 | 降低非矩阵指令工作与依赖 | 舍入/饱和、溢出、NaN/Inf、EXEC/lane mask、边界与别名；不能以减少指令放松数值契约 |

这是一组候选而非待完成清单。用 [上限与融合分析](performance-limits-and-fusion.md) 判断主要成本在工作量、交接还是等待：大头是重复数据流时，微调汇编不应代替必要的结构重写；结构合适但调度留有空间时，也不必重写整个算法。

## 3. 只有准备重建代码对象时，才做恢复与 ABI 检查

普通“读汇编→改源码”沿用正常构建，不需要额外重建原始二进制。直接编辑汇编/代码对象时，先验证工具链能处理当前目标，再投资大量搜索。

- **恢复的不只是指令正文。** 保留 ELF sections/symbols/notes、kernel descriptor、目标 code-object 版本与 metadata；准确恢复汇编声明和 PC-relative 控制流。插入、删除或重排时维护标签、分支目标、重定位与布局。
- **先验证未修改的往返。** 原对象→可编辑汇编→重新汇编/链接，核对指令体、descriptor 与 metadata。链接必然重算的字段单独解释，不忽略未知差异；再确认原 launcher 能加载，代表输入正确。工具链、目标或恢复方法改变后重新核对。往返不成立时修复恢复过程，或选择其他表达层，不把恢复错误当优化失败。
- **改动后资源描述一起更新。** 按目标工具链核对 VGPR/SGPR、适用时的 AGPR、LDS、scratch、wave/寄存器分配粒度及相关使能字段，保持 descriptor 与 metadata 一致；不能只按最大寄存器编号手填。动态 LDS 等还受 launcher 契约约束，资源增大后检查可启动性与并发代价。
- **保持接口或明确改变集成。** drop-in 候选保留导出符号、kernarg 布局/大小、启动几何及宿主可见约定。需要改参数/launch 时，将其作为新的工程实现路线并连同调用方验证，不能宣称原 ABI 下可直接替换。
- **受限补丁不是任意改字节。** 论文在无法完整重建时使用资源不变、大小不增加的补丁；这两个条件本身不充分。还需可靠工具处理编码长度、对齐、分支位移、重定位和入口，确认剩余空间/填充不被执行且描述仍正确。缺少这些能力就改走可重建汇编、inline asm 或源码路径，不能靠删元数据让对象可加载。

所有改写放任务内的独立副本和构建目录；通过可控 launcher/加载配置选择候选，保留原件。不要直接改系统安装库或共享 JIT 缓存。原对象和候选 SHA 用于证明测的是谁，不是性能原因；收益仍由实际计时与机制证据解释。

## 4. 保留正确性依据，复现真实 dispatch

**有独立数学/reference oracle 时继续使用。** 原二进制的差分结果可补充捕获 ABI、数值顺序或真实路径问题，不能替换独立 oracle，也不能随 best 改变容差。

只有源码/独立 reference 不可得时，才把冻结原对象 `K0` 作为行为参照，标明“已测输入下的差分一致”，不称数学正确性证明。不要为了套用 HIP 脚手架凭猜测另造一个接口或 reference。

- 参数与启动语义能可靠重建时，用代表 shape、stride、dtype、seed、尾块与边界输入建立独立测试。仅有 kernarg 偏移通常不能推断所有指针的 dtype、容量、方向与别名；不确定就追 launcher 或真实输入。
- MoE 路由、量化、混合 dtype、嵌套指针、workspace 或原地状态复杂时，捕获真实调用的 **执行前状态**：kernarg/标量、grid/workgroup、动态 LDS、有关设备缓冲及其 alias/指针关系。原件和每个候选都从同一状态运行，warmup/重复执行也核对状态恢复，不能复用已被上次执行改写的输入。
- 原始指针字节不能直接拿到另一个进程/分配里用。论文通过恢复原虚拟地址处理嵌套指针；当前 HCU 运行时不保证支持。可选择已验证的对象重建/指针重定位，或保留原应用 launcher，不编造一个“通用 replay”能力。
- 按原契约比较全部有效输出、整数/索引、应保持的只读输入及有关状态；未定义 padding、非确定性输出分别处理。浮点容差、舍入和特殊值政策来自任务，不照搬论文统一 cosine/L∞ 阈值；单个相似度不能掩盖局部大误差。
- canary/guard 能发现部分越界写，不能证明无越界读、race、死锁或异步错误。同步/流水修改补相应的项目测试与可用诊断，执行失败/超时保留原因；恢复不了的设备异常按环境流程处理，不反复向失效设备发测试。

本仓 `run_captured_kernel.py` 是 Triton 性能重放入口，不会自动完成上述代码对象捕获、固定地址恢复或差分 oracle。需要时在任务工程实现/复用专用 harness，并标出实际覆盖范围。

## 5. 把汇编实验接回已有优化循环

先完整构建与接口检查，再做正确性，最后进行未开启 profiler 的计时。复用原有多规模回归和独立交替对照，不增加第二套固定晋级阈值。HIP 工程仍遵守既有四轮确认；Triton 按其已声明的协议，不能把论文的接受率或一次最快值当晋级依据。

按实际需要留存：

```text
原始 K0 + 父候选身份 → 汇编/源码改动与构建命令 → 候选代码对象
→ 实际加载符号/gfx/产物 → 输入与 launcher → 正确性/样本/profile
```

复用已有 manifest/报告即可，不强制新增文件树。源码、恢复汇编/补丁、原/父/新对象的 SHA、完整工具链和资源描述应能追到同一次实验。多 kernel 或 fat binary 要定位确实替换的对象；重新编译/JIT/缓存命中后检查仍加载该候选。相同源码哈希不能区分两个不同的后编译补丁。

当前 HIP 自动编排围绕源码 `kernel.<ext>`、方法 registry 和构建收据，**没有自动恢复/改写 HSACO、维护二进制候选谱系或确认补丁实际加载的能力**。超出它能表达的实验走 [项目实验入口](architecture-search-and-experience.md#5-与现有脚本衔接)，另绑定真实产物与正确性/计时结果；不拿未变化的占位 HIP 源码冒充候选身份。扫描器读取了某个代码对象，不代表 benchmark 真正加载过它；不能只填构建收据就声称整个替换流程已支持，也不手改 state 为通过。

## 6. 从 AsmEvo 搜索方法中保留的轻量做法

- **区分失败阶段。** 汇编/链接失败、ABI/资源不一致、运行/数值错误、有效但不快、环境/采集失败分别记录，下一轮针对原因处理。环境故障不是一个优化假设被否定的证据。
- **按父版本保留候选。** 可从当前 best 或更早的有价值版本继续；best 与探索分开。不照搬每轮重置到 best 的实现，允许正确但暂慢的路线按 [架构探索指南](architecture-search-and-experience.md) 孵化。
- **组合后重新验证。** 两项局部优化各自有效，不代表合并仍正确或收益相加；即使改动行不重叠，也可能共享寄存器、等待计数或改变 occupancy。明确共同基底，逐步合并，对完整 kernel 和两父版本/当前 best 做同口径验证；不成立就保留独立候选。
- **按内容和条件去重。** 重复候选且输入/环境不变时复用已有诊断，减少无意义重试；编译参数、目标、输入或实现改变后可以重测。去重只省调查成本，不省最终采用版本所需的新鲜独立对照。
- **停滞时改变问题。** 区分没有新方案、选错热点、收益被噪声掩盖和工具失效；可换热点窗口、资源假设、表示层或起点。多 Agent、多起点和长预算是选择，不是前提；不复制论文固定四 worker/每 kernel 十二小时配置。

## 7. 交付为可复现实现

验证实际工程分派：候选是否命中、JIT 是否重新编译覆盖、是否走了 fallback，随后跑项目单测及实际端到端；replay 变快不等于模型变快。训练算子还保持原数值/阶段性精度验证，不把单 kernel 差分通过等同于 loss 验收。

记录支持的 gfx、工具链/库/特化版本和输入范围，提供构建/应用补丁与恢复原件的方法。若收益能稳定表达回 HIP/Triton/inline asm，比较维护成本后选择交付形式；保留目标专用汇编实现也可以。上游/编译器改变后重新生成并核对，不按旧偏移盲目套补丁。

## 8. 论文结论与采用边界

来源：用户提供的 *AsmEvo: Agentic Assembly-Level Optimization of AMD GPU Kernels with Functional Equivalence Verification*，arXiv:2608.20711v1，2026-08-21，共 9 页；[在线论文入口](https://arxiv.org/abs/2608.20711v1)。核读原 PDF 的 SHA256 为 `7dec6f1b7abeed25356c9f6d954c1c893a7c4c4c10e268075408d526e6d2066e`，以下页码为物理页。

| 位置 | 主要内容 | 本指南采用与限制 |
| --- | --- | --- |
| 第 3 页 | 原二进制为 oracle、完整对象恢复、往返、两级输入获取、资源元数据重建 | 补编译后优化路线；有数学 oracle 时继续保留；HCU 工具与 ABI 单独验证 |
| 第 4 页及图 1 | 热点窗口、受限补丁、正确性先于计时的执行器 | 用动态证据缩小上下文，局部编辑但全 kernel 验收；不把猜测当动态采集 |
| 第 5 页 | 谱系、多起点、组合复验、去重与停滞处理 | 提炼轻量搜索方法，不照搬团队规模、预算与每轮重置策略 |
| 第 6–7 页、表 2–3 | MI308X 上选定 30 个 KernelBench kernel 有 29 个改善，几何平均 1.35×、最高 3.88×；MI300X 的 4 个 AITer/4 个 Triton kernel 几何平均分别 1.09×/1.18× | 对照均为各自原编译对象；样本有限、硬件/实现不同，不能视为 HCU 预期收益，也不能据两组差异归因某编译器更差 |
| 第 7–8 页 | AITer 的等待/访存/转换机会、Triton 真实 dispatch 重放及框架加载验证 | 补源码调查与部署验证；论文未给出这些例子的完整逐条补丁，不能编造具体指令 diff 或把 kernel 收益写成训练端到端收益 |

论文的核心价值是允许在编译完成后继续搜索，并把对象恢复、执行验证和实验身份连起来；它提供已测输入上的经验等价，不是形式化验证，也未证明所有 shape、架构或训练数值等价。本文是结合既有 HCU Skills 的工程提炼，并未安装 AsmEvo、实现它的完整自动系统或声称在 HCU 上复现了结果。

外部方法/工程先按需在线读论文或 GitHub 的固定版本文档、相关源码；只有运行、调试或离线查证确实需要时才下载到任务工作区并记录版本。KRA 的入口与适用边界见 [可选工具说明](performance-limits-and-fusion.md#7-按需复用-kra-工具)。阅读这些资料不要求安装新依赖，不把外部仓库和测量缓存复制进 Skill。
