# 架构探索与实测经验复用

用于接手参考、生成基线转入优化、局部收益停滞及跨会话恢复。目标是让结构选择可以被实验推翻，让测到的经验可复用；探索深度和顺序由当前算子、证据与预算决定。本指南不要求多 Agent、固定课程或先冻结完整架构。

## 1. 两种参考起点

| 起点 | 可以继承什么 | 需要警惕什么 | 合理的初始动作 |
| --- | --- | --- | --- |
| 有当前任务适用证据的专家高性能参考 | 已验证的数据流、分块/调度机制、工程接口和失败边界 | 原硬件/shape/版本的取舍可能在当前 HCU 上形成上限；熟悉的结构也会造成锚定 | 阅读可用源码、运行并定位实际路径，理解为什么快；针对剩余瓶颈选择局部或结构实验 |
| 生成的保守 HIP 正确性基线 | 数学语义、接口适配、原始 reference、测试和复现方式；均以实际验证状态为准 | 一线程一输出、串行归约、重复读或多次写回常是易验证的选择，并未证明适合作为性能架构 | 正确性成立后尽早检查结构假设；允许从现有 HCU 库或不同数据流重新实现，再做局部调优 |

来源与质量分开判断：人工代码也可能只是朴素实现，生成代码也可能复用了成熟路径。仅在 CUDA 等其他硬件上很快的参考，机制可参考，当前 HCU 性能仍待验证。可用的专家源码不必人为屏蔽；没有高质量参考时也不强求先找到一个。

接手生成工程时读取 `baseline_manifest.json` 的来源、`optimization_handoff`、未解决假设和实际验证记录。旧产物没有交接字段时根据源码与日志判断，缺字段不代表高性能参考，也不要求重新生成基线。

数学 oracle、冻结的对照基线、已确认的性能 best、当前探索版本各有用途。性能 best 晋级只改变实现起点；不据此重新生成 oracle、放松精度或改变输入分布。新 run 沿用原数学契约，环境或计时口径变化则重建可比较测量，保留与旧实验的关系。

## 2. 把架构选择变成可以推翻的假设

在已有 `analysis.md` 中简要写清当前结构为何可能合适、哪项观察会推翻它。只写影响当前决策的内容，例如任务如何划分、数据如何驻留与复用、kernel 如何拆分/融合、计算与同步如何组织；不要求每个算子填完一张通用架构表。

**参数变化不等于结构探索。** 改 tile、block 或 stages 有时会触及结构，但也可能始终保留相同的数据流与串行路径。判断依据是限制吞吐的工作或依赖有没有机会被改变，而不是参数名称或改动行数。

以下现象值得重审结构，不是自动判定架构错误：多个局部变体的收益都落入噪声；资源或串行路径限制长期不变；与可比实现有明显差距；某些 shape 反复回退。先排除测量、实现错误和调度干扰，遵守 [瓶颈采集要求](hcu-workflow-contract.md#5-性能分析层次与工具)，再选择最有区分力的实验。

- 用小探针回答具体问题，例如当前供数路径能否支持目标吞吐、某个布局是否触发额外转换、拆分是否获得足够并行性且抵消合并开销。只隔离与当前假设有关的因素，保留准确目标、源码/构建、输入、命令和原始结果。
- 探针在目标 HCU 上执行，选择能区分候选解释的指标或时间线；benchmark、profile、资源/ISA 分别承担自己的证据角色。微基准通过不证明完整算子获益，移回真实实现后还要验证。
- 估算结构改变可能消除的工作及新增成本，用来决定是否值得投入；估算与实测分开，不能用未核对的峰值宣布已经到顶。证据足够时直接做端到端结构实验，不强制先造一个探针。

例如，朴素 GEMM 的多个 block size 都没有改善重复加载和标量计算路径时，继续扫 block 未必有价值；可调查适合当前精度/目标的分块复用或矩阵计算路径。成熟归约实现变慢则可能来自网格规模、合并、资源压力等不同原因，应由实际输入与采集决定是否拆分或重排，不能统一指定 split、融合或某个指令。

结构假设得到支持后，可暂时集中局部调优以控制成本；出现反证时允许重开。收益停滞时重看限制问题的假设，不要求机械地“每隔几轮重写”，也不要求先穷尽局部参数。

## 3. 允许跨越暂时回退，保持 best 可交付

将已确认 best 与探索分支分开。结构改变可能需要数据布局、供数和调度协同完成；第一步正确但更慢，不能据此否定整条路线。给仍有证据支持的路线留下源码快照、父版本、当前结果、尚缺环节和下一项可验证实验，可以继续孵化。

- **完整且正确，暂时较慢**：可保留探索，不晋级；说明剩余机会来自何种机制，以及何种结果将终止这条路线。
- **尚未完整、编译或正确性失败**：保留为明确标记的开发中草稿，不能当作正确候选、有效消融或已验证经验。
- **已有完整实现和稳定收益**：进入原有多用例正确性、回退上限、独立交替对照及必要工程验收；筛选时间不直接决定 best。

是否继续由预期机会、已消耗成本和剩余预算决定。不要因每一步必须立即更快而过早回滚，也不因“可能还有潜力”无限保留路线。失败只否定实际测过的实现与条件，不自动否定整个方法族。

## 4. 让实测经验跨轮、跨会话复用

在任务工程维护一个轻量入口，例如已有报告中的经验段或 `experience.md`，链接到 run 和原件。每轮只在出现新事实、反例或决策变化时更新；恢复/收尾时确保入口足以找到当前 best 与未完路线，不要求每次调参另填表。

一条有用记录能回答：

- **测到了什么**：观察值及变化，或失败现象；与“可能因为……”的机制假设分开。标明来源是本轮实测、历史实测、源码/文档还是估算。
- **在什么条件下**：相关 gfx/设备、编译器/DTK/库版本、shape/dtype/layout、数值政策、计时/采集方式。只展开影响可迁移性的条件，完整环境链接到原件。
- **如何复查**：固定源码/构建身份、探针或候选路径、命令、原始 bench/profile/ISA 及必要的对照。工程已有 SHA/清单直接引用，不重复制作。
- **下一次怎么用**：适用边界、已见反例、仍待验证的问题、值得继续的分支。记录关键架构假设的取舍依据和重开条件，无须保存冗长对话。

压缩上下文时保留观察、条件和原件入口；不要把模型解释写成测量事实。某个 shape 上更慢的 swizzle、split 或流水不是跨算子禁用规则，改变布局/资源/编译器后可以有理由重试。

下一次开始时按问题检索相关记录，核对适用条件，决定直接复用机制、先复现探针还是重新实验。相同条件的记录可减少重复试错；历史计时不替代当前 best 晋级所需的新鲜对照。条件不匹配的经验可提供假设，不能直接证明当前兼容或收益。

任务记录支持同工程多 run 和相关算子复用；跨工程只使用已知且可访问的记录位置，迁移时连同最小复现实验和必要原件，不能只带一句结论。共享 HCU-Knowledge 的整理/发布是另一个维护流程，不因记录本地经验自动写入；Skill 本身不积累某次任务的测量值。

## 5. 与现有脚本衔接

现有脚本是实验工具，并未实现自动架构搜索或经验检索：

- 标准 `methods.json` 按 registry 校验，同一轮共用方法组合；`branch_explore.py` 选择一个 champion。局部变体沿用此流程，不把互不相同的架构混在同轮、再用同一方法清单归因。
- 不同结构路线放独立实验目录，能由现有方法描述的可分轮测试。`frontier` 和旧分支源码可作为继续探索的起点，现有编排不会自动选它们；矩阵回退门禁过滤掉的正确实现也未必进入 frontier，需要显式保留。
- 目录不足以表达新算法/结构时，用任务工程的独立 benchmark/实验入口保留完整实现、假设与原件。不要伪装成某个无关的注册方法，也不为单次实验修改共享 registry。项目入口同样遵守 [共同测量契约](hcu-workflow-contract.md#4-测速与多规模比较) 与 [产物身份要求](experiment-artifacts.md#自定义-benchmark-接口)，最终对冻结 baseline 和当前 best 做同口径确认；不能借此绕过正确性、逐例回退或四轮独立对照。
- 外部实验结果不自动写回 `state.json`；需在任务报告中记录确认结果、支持范围和采用版本，不手工篡改脚本的已确认状态。新 run 可以从其已确认实现出发，但保留原 oracle、原基线与谱系，不把重新 seed 的计时当作跨 run 晋级证明。
- 探索分支在完成联动改动前可以不 close；阶段计时和正确性状态如实保留。该分支是否继续不由“本轮没打败 best”单独决定；预算约束和最终验收仍有效。

这些衔接允许当前 Skill 运用方法论，不承诺脚本已经自动持久化经验、跨 run 选路或管理多条孵化路线。

## 来源与采用范围

借鉴 ForgeKernel 固定版本 `5030503d3ff71851aa34c14b9caf13ebfa9d9a78` 中的结构侦察与重开、保留暂时回退的探索实现、持久化硬件经验等机制。上游 [README](https://github.com/OpenBMB/ForgeKernel/blob/5030503d3ff71851aa34c14b9caf13ebfa9d9a78/README.md#highlights) 也规定 M0 架构冻结；[优化循环](https://github.com/OpenBMB/ForgeKernel/blob/5030503d3ff71851aa34c14b9caf13ebfa9d9a78/src/forgekernel/loop/driver.py) 区分开发中状态与已正确路线，并保留性能回退以继续构建。

这里提炼的是可按算子使用的方法，没有照搬其固定 Teacher/Student 课程、M0 冻结、NVIDIA 专用路径或将 best 改作新数学 reference 的做法；保留 HCU 的独立 oracle 和验收要求。这是流程设计，收益仍需实际算子实验验证。
